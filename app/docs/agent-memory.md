# Treasure Hunt — memoria de la aplicación

## Regla absoluta de endpoints

Los guiones (`-`) están totalmente prohibidos en todos los segmentos de endpoints. Los
conceptos compuestos se modelan con recursos anidados en inglés, por ejemplo
`/api/clients`, nunca `/api-clients`. No crear rutas ni aliases con guiones; una ruta
existente que los use es deuda que debe corregirse, no un precedente que copiar.

## Alcance

Treasure Hunt es una aplicación móvil de búsquedas del tesoro geolocalizadas con interacciones de realidad aumentada.

El desarrollo comienza con Android. La aplicación iOS se mantiene prevista, pero no forma parte de la primera etapa.

La primera prueba de concepto debe validar la parte técnicamente más incierta: reconocer un objetivo físico mediante imagen de referencia, texto OCR, marcador visual y una combinación de esas evidencias; después debe fijar contenido de realidad aumentada sobre el objetivo reconocido.

## Principios

- Trabajar en tareas pequeñas, verificables y revisables.
- Resolver primero los riesgos técnicos principales antes de construir el flujo completo del producto.
- Mantener separadas la aplicación móvil, el frontend y el backend.
- Modelar conceptos del juego, no detalles accidentales de una tecnología.
- No generalizar una capacidad hasta que exista más de un uso real que la comparta.
- Ejecutar reconocimiento y validaciones localmente cuando sea razonable.
- Una detección aislada no debe considerarse suficiente: debe existir estabilidad temporal y evidencia observable.
- La aplicación debe explicar en modo diagnóstico qué reconoció y por qué aceptó o rechazó el objetivo.

## Organización de proyectos

### Producto `treasurehunt`

Contiene todo lo específico del producto Treasure Hunt:

```text
treasurehunt/
├── app/
│   ├── android/
│   └── ios/
├── backend/
├── frontend/
├── platform/
```

- `app/android`: aplicación Android, primera plataforma que se implementará.
- `app/ios`: reservado para una implementación posterior; no desarrollarlo todavía.
- `frontend`: sitio web específico de Treasure Hunt. En el futuro generará el QR utilizado para obtener una cacería.
- `backend`: reservado para el servidor propio del producto cuando exista.
- `platform`: checkout de Plataforma para cambios compartidos requeridos por este producto.
- `scripts`: herramientas operativas del producto, incluido el empaquetador de fuentes.

### Repositorio `cabezudo.dev`

- Las funciones de backend específicas de juegos pertenecen al módulo `games`.
- Las funciones exclusivas de Treasure Hunt se organizan bajo el dominio o paquete `games.treasurehunt`.
- Una función solamente debe trasladarse a `platform` cuando sea realmente común a varios módulos o productos.
- El motor y editor de aventura 2D continúan separados dentro de `games`; no deben mezclarse con Treasure Hunt.

## Flujo de producto previsto

1. La persona instala la aplicación.
2. Registra el dispositivo mediante correo usando `device-client` y el flujo de registro ya implementado para SaleMejor.
3. Escanea un QR generado por el frontend de Treasure Hunt.
4. La aplicación obtiene del backend la cacería identificada por el QR.
5. Presenta únicamente la pista o etapa actual.
6. La persona se dirige al lugar indicado.
7. Al llegar, busca el objetivo físico y lo observa con la cámara.
8. La aplicación valida ubicación, objetivo visual y actividad según las reglas de esa etapa.
9. La aplicación muestra contenido de realidad aumentada o una nueva instrucción.
10. Al completar la etapa, guarda el progreso y desbloquea la siguiente.

Este flujo describe la dirección del producto, pero no forma parte completa de la primera prueba de concepto.

## Decisiones actuales

- El QR será el mecanismo inicial para seleccionar u obtener una cacería.
- El QR se generará en el frontend de Treasure Hunt.
- Treasure Hunt utilizará el registro por correo de `device-client`.
- La primera aplicación será Android.
- iOS se implementará después.
- `games` seguirá siendo el módulo backend general para juegos.
- La realidad aumentada es una capacidad de Treasure Hunt, no un tipo general de juego por sí misma.
- GPS, reconocimiento visual y resolución de una actividad son evidencias diferentes y no deben confundirse.
- No se presupone que cualquier puerta, ventana, rincón o banca pueda reconocerse de manera confiable a partir de una sola fotografía.
- La aplicación Android es un proyecto nativo Kotlin con Jetpack Compose, nombre `Treasure Hunt`, paquete y `applicationId` `dev.cabezudo.treasurehunt`.
- La base Android usa AGP 9.2.1, Gradle Wrapper 9.4.1, Kotlin Compose Compiler 2.3.20, Compose BOM 2026.06.00, `compileSdk` 36 y `targetSdk` 36. Estas versiones compilan con el SDK y JDK 21 instalados; el bytecode de la aplicación se limita a Java 17.
- Android conserva `minSdk` 24 como línea base ya validada y compatible con una futura capacidad ARCore opcional; CameraX soporta esta línea base sin requerir ARCore.
- La cámara base usa CameraX `1.6.1`, versión estable confirmada, mediante `camera-camera2`, `camera-lifecycle` y `camera-view`. La vista previa estándar debe funcionar aunque Google Play Services para RA no exista o el dispositivo no sea compatible.
- La preparación monocromática usa el AAR oficial `org.opencv:opencv:5.0.0.1` publicado en Maven Central por OpenCV Team/OpenCV.org. El POM enlaza el repositorio `opencv/opencv`; no se usan wrappers ni distribuciones de terceros. Esta versión compila con el `minSdk 24` y el toolchain existentes.
- El OCR latino local usa `com.google.mlkit:text-recognition:16.0.1`, artefacto estable oficial de Google. Es la variante bundled: el modelo queda enlazado estáticamente en el APK, está disponible de inmediato y no requiere descarga inicial ni un servicio OCR remoto. El APK construido contiene `libmlkit_google_ocr_pipeline.so` y `assets/mlkit-google-ocr-models` para cada ABI empaquetada.
- El objetivo controlado de reconocimiento se llama `guardian_door_target`: el PNG exacto de `1200 × 1600 px` vive en `res/drawable-nodpi` para impedir escalado automático y su fuente determinística SVG usa el mismo lienzo. Su tamaño físico nominal es `180 × 240 mm` al imprimir sin ajuste. Es una composición propia, asimétrica, de alto contraste, con detalles distribuidos, el texto `PUERTA DEL GUARDIÁN 27` y una reserva delimitada que todavía no contiene un marcador ArUco válido.
- El reconocimiento aislado usa ORB, `BFMatcher` Hamming, KNN con dos vecinos, prueba de razón, homografía RANSAC y validación geométrica explícita. Se limita inicialmente a `7.5` análisis por segundo; no incluye estabilidad temporal ni acepta progreso.
- El SDK oficial `com.google.ar:core:1.54.0` se conserva únicamente para detectar capacidad. La aplicación está configurada como AR Optional mediante `android.hardware.camera.ar` con `required=false` y el metadato `com.google.ar.core=optional`. No crea una `Session`, no abre la cámara con ARCore y no solicita instalar ni actualizar Google Play Services para RA.
- La arquitectura de cámara separa `CameraPermissionController`, `ArCoreCapabilityDetector`, `CameraPreviewController`, `CameraRuntimeController`, el estado y mapeo diagnóstico y la presentación Compose. `MainActivity` sólo registra el permiso, conecta esas piezas y reenvía el ciclo de vida.

## Primera prueba de concepto Android

### Objetivo

Demostrar que la aplicación puede reconocer un objetivo físico, determinar una pose utilizable y mantener un elemento virtual visualmente unido al objetivo mientras se mueve la cámara.

### Fuera de alcance

La primera prueba no incluirá:

- registro del dispositivo;
- comunicación con el backend;
- lectura del QR de la cacería;
- GPS;
- mapas;
- progreso persistente;
- editor o administración de cacerías;
- aplicación iOS.

### Objetivo físico inicial

Usar una superficie plana, fija y controlada, colocada sobre una pared o puerta. Debe contener:

- una imagen con suficientes detalles visuales;
- un texto distintivo conocido;
- un marcador visual con identificador conocido;
- dimensiones físicas conocidas.

Después de validar este objetivo controlado se probarán superficies reales y se retirarán gradualmente las ayudas artificiales.

### Modos experimentales

La aplicación debe permitir probar separadamente:

1. **Imagen de referencia:** reconocer la superficie y obtener su posición y orientación.
2. **OCR:** encontrar y validar el texto esperado.
3. **Marcador visual:** identificar el marcador y obtener una pose de referencia.
4. **Combinación:** reunir las evidencias anteriores mediante una regla explícita.

Los primeros candidatos técnicos son ARCore Augmented Images para imágenes planas, ML Kit Text Recognition para OCR local y un marcador ArUco para detección determinista. Son candidatos de la prueba, no decisiones irreversibles de arquitectura.

### Regla combinada inicial

La combinación no debe implementarse como una dependencia rígida de las tres señales en cada cuadro. Debe registrar cada evidencia por separado y exigir estabilidad durante un intervalo configurable.

Una hipótesis inicial para experimentar es aceptar dos evidencias compatibles entre:

- imagen de referencia;
- texto esperado;
- marcador esperado.

La hipótesis debe validarse con pruebas antes de convertirse en regla del juego. La fuente de la pose puede tener prioridad independiente de la regla de identidad; inicialmente el marcador puede proporcionar la pose más determinista y la imagen servir como alternativa.

### Diagnóstico mínimo

La pantalla de prueba debe mostrar como mínimo:

- estado de reconocimiento de imagen;
- texto reconocido y resultado de su comparación;
- identificador del marcador encontrado;
- estado de seguimiento y pose;
- evidencias acumuladas;
- tiempo hasta la detección;
- decisión final;
- motivo de aceptación o rechazo.

### Condiciones de prueba

Probar al menos:

- diferentes distancias;
- ángulos frontales y oblicuos;
- iluminación fuerte y débil;
- movimiento de cámara;
- objetivo parcialmente oculto;
- pérdida y recuperación del seguimiento;
- una fotografía del objetivo mostrada en otra pantalla.

### Criterio de terminación

La prueba se considera terminada cuando:

1. Los tres mecanismos pueden evaluarse por separado.
2. La aplicación presenta la evidencia de cada mecanismo.
3. Existe una combinación configurable y explicable de evidencias.
4. Un objeto virtual sencillo queda fijado sobre el objetivo aceptado.
5. El seguimiento se recupera razonablemente después de perder temporalmente el objetivo.
6. Se documentan los casos en los que cada mecanismo funciona o falla.

## Estado actual

- `app/android` y `app/ios` son directorios hermanos separados. Android es la plataforma activa; `app/ios` permanece vacío y aplazado.
- `app/android` contiene un proyecto Android nativo mínimo con un solo módulo `app`, Gradle Wrapper completo y un `.gitignore` que conserva los archivos del Wrapper.
- La única actividad es `MainActivity`; muestra un `PreviewView` de CameraX y un panel Compose superpuesto. El panel separa permiso, estado y resolución de `Preview`, estado y resolución de `ImageAnalysis`, rotación, formato, planos, cuadros totales, cuadros del último segundo, FPS aproximados, antigüedad del último cuadro, disponibilidad ARCore, modo activo y causas de error.
- CameraX es el único propietario de la cámara. `CameraPreviewController` selecciona la cámara trasera, configura `PreviewView` con `FIT_CENTER` y vincula `Preview` e `ImageAnalysis` juntos en una sola llamada a `bindToLifecycle`. Los metadatos de ambos flujos se mantienen separados porque sus resoluciones pueden diferir.
- `ImageAnalysis` usa `STRATEGY_KEEP_ONLY_LATEST`, salida `YUV_420_888`, estrategia de resolución con objetivo `640 × 480` y fallback al tamaño compatible más cercano, y la misma rotación objetivo que `Preview`. En el teléfono la resolución real seleccionada para análisis fue `640 × 480`, con tres planos; `Preview` conservó `960 × 720`.
- `CameraFrameAnalyzer` valida cada `ImageProxy` YUV, coordina su preparación para OpenCV y siempre lo cierra en `finally`. No convierte YUV a RGB ni conserva el cuadro después del callback. Usa tiempo monotónico para intervalos, FPS y duraciones.
- `LuminancePlaneCopier` copia exclusivamente el plano Y a un arreglo compacto. Trabaja sobre un `ByteBuffer.duplicate()`, respeta posición, límite, `rowStride`, `pixelStride` y padding, valida el último byte accesible y no modifica la posición compartida. No presupone strides contiguos.
- `OpenCvFrameConverter` crea un `Mat` `CV_8UC1` con la luminancia compacta y aplica `Core.rotate` para `90`, `180` o `270`; `0` conserva las dimensiones. La cámara trasera no se refleja. El `Mat` fuente temporal se libera después de rotar; `OpenCvFrame` posee el resultado y su `close()` ejecuta `release()`. El analizador consume cada `OpenCvFrame` mediante `use`, de modo que ningún `Mat` sobrevive al cierre del `ImageProxy`.
- La muestra diagnóstica se obtiene antes de liberar el `Mat`, se reduce a un `ByteArray` administrado y se publica como máximo una vez por segundo. Compose crea únicamente la representación ARGB necesaria para mostrar esa muestra monocromática; no se acumulan muestras ni buffers históricos.
- `FrameMetricsAccumulator` conserva contadores y únicamente una ventana de llegadas del último segundo, sin guardar imágenes ni todos los cuadros. Publica diagnóstico como máximo cada 250 ms; la muestra agrega como máximo una publicación por segundo. Los estados de análisis son `IDLE`, `STARTING`, `RUNNING`, `PAUSED`, `CLOSED` y `ERROR`. Un error de conversión se publica con causa concreta y el siguiente cuadro vuelve a intentarse.
- El análisis corre en un `ExecutorService` de un solo hilo llamado `treasure-hunt-frame-analysis`, independiente del hilo principal. Al cerrar el controlador se elimina el analizador del use case, se desvinculan los casos de uso, el analizador pasa a `CLOSED` y el executor recibe `shutdown()`.
- La ruta anterior de `Session`, OpenGL y tracking ARCore permanece eliminada. ARCore sólo se consulta como capacidad opcional y no comparte ni abre la cámara.
- El selector actual elige determinísticamente `STANDARD_CAMERA` tanto si ARCore está disponible como si está ausente, no instalado o no es compatible. `ARCORE` permanece como valor de modo reservado, sin una ruta funcional en esta tarea.
- Existen veinticinco pruebas unitarias JUnit 4 con 0 fallos: las quince anteriores, seis para copia del plano Y —contiguo, padding, `pixelStride > 1`, posición inicial, buffer insuficiente y dimensiones/strides inválidos— y cuatro para contenido y dimensiones resultantes de rotaciones `0`, `90`, `180` y `270`.

Exige `STANDARD_CAMERA`, CameraX `STARTED`, análisis `RUNNING`, OpenCV `READY`, al menos un cuadro preparado, dimensiones positivas y ausencia de error de conversión. ## Diccionario / Glosario

- **Cacería:** búsqueda del tesoro completa que contiene una secuencia o red de etapas.
- **Etapa:** unidad de progreso que presenta una pista y establece condiciones para completarla.
- **Pista:** información que guía a la persona hacia un lugar, objetivo o actividad.
- **Objetivo físico:** elemento real que debe localizarse y observarse, como una puerta, placa, ventana o banca.
- **Imagen de referencia:** representación visual conocida utilizada para identificar una superficie u objeto.
- **OCR:** reconocimiento óptico de caracteres utilizado para extraer texto de la cámara.
- **Marcador visual:** patrón artificial identificable que ayuda a confirmar identidad, posición y orientación.
- **Evidencia:** resultado observable producido por un mecanismo de reconocimiento.
- **Pose:** posición y orientación estimadas de un objetivo en el espacio.
- **Anclaje:** referencia espacial usada para mantener un elemento virtual unido visualmente al mundo real.
- **Contenido aumentado:** información u objeto virtual mostrado sobre la imagen de la cámara.
- **Estabilidad temporal:** requisito de que una evidencia se mantenga durante varios cuadros o un intervalo, evitando aceptar detecciones aisladas.
- **PoC:** prueba de concepto destinada a validar viabilidad técnica, no a entregar todavía el producto completo.
